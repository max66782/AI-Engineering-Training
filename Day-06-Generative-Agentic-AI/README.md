# Day 6 — Generative & Agentic AI

## Objective

Build a simple agentic AI system that uses Gemini to understand a user's request, decide when an external tool is required, execute a GitHub API tool, and use the tool result to generate a final response.

---

## What I Learned

### 1. Generative AI

Generative AI refers to AI systems that can generate new content based on a user's input.

Examples include:

- Text generation
- Code generation
- Summarization
- Question answering
- Content generation

In this project, Gemini is used as the generative AI model.

---

### 2. Agentic AI

Agentic AI is a system that can work toward a goal by reasoning about the task, selecting actions or tools, executing them, observing the results, and producing a final response.

A basic agentic workflow is:

    User Goal
        ↓
    LLM Reasoning
        ↓
    Select Tool
        ↓
    Execute Tool
        ↓
    Observe Result
        ↓
    LLM Generates Final Response

Unlike a simple chatbot, an agentic system can interact with external tools and use the results of those tools to complete a task.

---

## Generative AI vs Agentic AI

| Generative AI | Agentic AI |
|---|---|
| Generates content | Performs actions toward a goal |
| Usually responds to a prompt | Can decide what action/tool is required |
| Does not necessarily interact with external systems | Can interact with APIs, databases, tools, etc. |
| Example: Generate Python code | Example: Call GitHub API and summarize repositories |

---

## What Is a Tool?

A tool is an external capability that an AI system can use to perform an action or retrieve information.

Examples:

- Weather API
- Database query
- Calculator
- Search API
- GitHub API
- File system operations

In this project, the tool is:

    get_github_repositories(username)

It retrieves the public repositories of a GitHub user.

### `tools/github_tool.py`

Contains the actual GitHub API integration.

The main function is:

    get_github_repositories(username)

It:

1. Builds the GitHub API URL
2. Sends an HTTP GET request
3. Handles a non-existent GitHub user
4. Raises errors for other unsuccessful HTTP responses
5. Returns structured repository information

The returned data contains:

- name
- url
- description

# Tool Calling

The Gemini model is given a tool declaration describing:

    Tool name:
    get_github_repositories

    Argument:
    username

The model can then generate a structured function call such as:

    get_github_repositories(username="torvalds")

The Python program extracts the generated argument:

    function_call.args["username"]

and passes it to the actual Python function:

    result = get_github_repositories(
        function_call.args["username"]
    )

This creates a separation between:

    LLM → decides what tool to call
    Python → actually executes the tool

---

# Tool Result Handling

After the GitHub tool executes, its result is returned to Gemini using a function response.

The tool result is structured as:

    {
        "repositories": result
    }

Gemini then uses this information to generate the final user-facing response.

This creates the complete tool-calling loop:

    User Query
        ↓
    Gemini
        ↓
    Function Call
        ↓
    Python Tool
        ↓
    GitHub API
        ↓
    Tool Result
        ↓
    Gemini
        ↓
    Final Response

---

# Error Handling

The GitHub tool handles a non-existent username explicitly.

    if response.status_code == 404:
        return {"error": f"GitHub user '{username}' not found."}

This prevents a GitHub 404 from producing an unnecessary Python traceback.

For other HTTP errors:

    response.raise_for_status()

is used.

The agent also checks whether Gemini actually requested a tool:

    if not function_call:
        print("Gemini did not request a tool.")
        print(response.text)
        exit()

This prevents the program from blindly trying to execute a tool when Gemini has returned a normal response.

# Important Debugging Lessons

## 1. Function Calls Are Not Guaranteed

The model may sometimes return normal text instead of requesting a tool.

Therefore, the code checks whether a function call exists before executing it.

---

## 2. The Tool Result Must Be Sent Back to the Model

Calling the tool is not the end of the agent workflow.

The result must be returned to Gemini so that Gemini can interpret the data and generate a natural-language response.

---

## 3. The Original User Request Must Be Preserved

When sending the tool result back to Gemini, the original user query and the model's function-call content are included.

This maintains the correct conversation structure for the function-calling workflow.

---

## 4. External APIs Can Fail

GitHub can return errors such as:

    404 Not Found

Therefore, external API responses should always be handled explicitly.

---

## 5. Model Availability Can Be Temporary

During testing, Gemini occasionally returned:

    503 UNAVAILABLE

with a message indicating that the model was experiencing high demand.

This was a temporary model availability issue rather than a GitHub tool or application logic failure.

Retrying the request later allowed the application to work normally.

# Conclusion

Day 6 introduced the core concepts behind Generative AI and Agentic AI.

The project demonstrates how an LLM can go beyond generating text by deciding when an external tool is required, generating structured tool arguments, executing the tool through Python, receiving the result, and using that result to produce a final response.

This provides the foundation for more advanced agentic systems using multiple tools, multiple agents, and frameworks such as LangChain and LangGraph.
